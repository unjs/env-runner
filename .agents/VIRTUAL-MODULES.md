# Virtual Modules (Node + Bun + Deno + Miniflare runners)

In-memory ES modules served via a `data.virtual` map. Shared across the node-worker, node-process, bun-process, and deno-process runners (plus the vercel/netlify runners built on the node-worker worker), with a separate host-side path for miniflare.

## Source files

- **`src/common/virtual-modules.ts`** — `async registerVirtualModules(virtual?)`: registers virtual modules when a non-empty `data.virtual` map is present, picking a backend by feature detection. Preferred backend is Node's `module.registerHooks()` with `createVirtualHooks()`, **feature-detected via a dynamic `import("node:module")`** (never a static named import, which would throw at link time on runtimes without it — Node < 22.15/23.5, older Deno). When `registerHooks` is absent but `Bun.plugin` exists (Bun), each map entry is registered via `build.module()` instead — mid-program registration affects subsequent dynamic imports, which is all the workers need (do NOT detect Bun via `module.register`: it exists there but is a silent no-op). The Bun `build.module()` load callbacks read sources from a live module-level map (`_bunVirtual`), not captured strings. **Module formats are derived from the specifier extension** (`virtualModuleFormat()`): `.ts`/`.mts` → TypeScript, `.json` → JSON module, else plain ESM. On Bun: `ts` loader for TypeScript; for JSON the runtime `json` loader does NOT parse contents (it would be parsed as JS), so the parsed value is served via the `object` loader as `{ exports: { default } }`. On Deno, custom load hooks **ignore the returned `format`** (every source parses as plain JS), so `_transformForDeno()` rewrites the map before registration: `.json` sources become `export default JSON.parse(...)` wrappers, and `.ts`/`.mts` sources are stripped with `module.stripTypeScriptTypes` (Deno >= 2.8.2) — on older Deno without it they **throw** (Deno's native type stripping is unreachable from hooks and no stripper dependency is bundled — callers must pass pre-transpiled JS). When neither backend exists, logs a one-time warning and skips registration. **Resolves to an idempotent unregister function**: `deregister()`s the registerHooks registration, or detaches `_bunVirtual` on Bun (no plugin-removal API — cached modules stay, but fresh loads throw and `refreshVirtualModule` stops matching); the workers call it from their `shutdown` handlers before posting the `exit` event. registerHooks-backend registrations are tracked in a stacked `_hooksRegistrations` array (latest first), so multiple simultaneous registrations stay individually invalidatable and unregistering one doesn't orphan the others (the Bun backend stays latest-wins — pre-existing limitation of the single `_bunVirtual` map). Also exports `refreshVirtualModule(specifier)`: re-registers a single Bun-backed specifier (Bun busts the module cache on override) and returns `false` on non-Bun backends — used by `_importFresh()` because Bun matches `build.module` keys verbatim, so a `?query` cache-buster would fail to resolve. And `invalidateVirtualModule(specifier, source?)`: invalidates a module in an active registration so its **next import evaluates fresh** (importers must be re-imported, e.g. via `reloadModule()`), optionally replacing the stored source. The invalidation is expanded via `expandVirtualInvalidation()` to every virtual module that **transitively imports** the specifier (otherwise a reloaded entry would resolve an intermediate importer to its cached instance, still linked to the old module) — on the registerHooks backend the per-specifier versions consulted by the resolve hook are bumped (an updated source goes through the same Deno transform as registration); on Bun it updates `_bunVirtual` and re-registers the expanded set; returns `false` for unregistered specifiers. `handleInvalidateModule(message, sendMessage)` wraps it for the workers' `invalidate-module` IPC handler (shared ack shape + error string). Shared by the node-worker, node-process, bun-process, and deno-process workers (all `await` it before importing the entry)
- **`src/virtual-loader.ts`** — `createVirtualHooks(virtual, versions?)`: builds synchronous ESM `resolve`/`load` hooks (`ResolveHookSync`/`LoadHookSync`) that serve virtual modules from a resolved `Record<string, string>`. A specifier present in the map (e.g. `#virtual-import`) resolves to a `virtual:<encoded-specifier>` URL and loads the stored source, short-circuiting default resolution; everything else falls through to `nextResolve`/`nextLoad`. The optional `versions` map (live, owned by `registerVirtualModules`) appends `?v=<n>` outside the encoded specifier when a module has been invalidated, so the same plain import resolves to a fresh module identity. The load `format` comes from `virtualModuleFormat(specifier)` (also exported): `.json` → `"json"`, `.ts`/`.mts` → `"module-typescript"` (Node's native type stripping, >= 22.18 / 23.6), else `"module"`. Node does not require the `with { type: "json" }` attribute for hook-served JSON modules (but accepts it). Map lookups strip a `?query` suffix (so a reload cache-buster like `#entry?__envRunnerReload=1` still matches `#entry`) while keeping the full specifier in the URL for a distinct module identity. Also defines `VirtualModuleSource` (`string | (() => string | Promise<string>)`), `VirtualModules` (`Record<string, VirtualModuleSource>`), `resolveVirtualModules(virtual)` which invokes/awaits factory sources into a plain `Record<string, string>` (the hooks run synchronously, so factories must be resolved ahead of time), `expandVirtualInvalidation(virtual, specifier)` which expands an invalidated specifier to itself plus its transitive virtual importers (quoted-occurrence scan of the virtual sources; over-matching is harmless — a bumped version only forces a re-evaluation), and `stripVirtualTypeScript(specifier, source, stripFn, hints)` — the shared TS-strip guard (clear `TypeError` with a backend-specific hint) used by the Deno transform and the miniflare runner

> See also [`base-runner.ts`](../AGENTS.md) in the main architecture list for the host-side `_resolveVirtualData()` / `_initWithVirtualData()` / `_refreshVirtualSource()` plumbing, and [`worker-utils.ts`](../AGENTS.md) for `isVirtualSpecifier()` / `_importFresh()` reload handling.

## How it works

Pass a `data.virtual` map (`specifier => source`) to the `node-worker`, `node-process`, `bun-process`, and `deno-process` runners (plus the `vercel`/`netlify` runners built on the node-worker worker) to serve in-memory ES modules. Each source is either a string or a factory `() => string | Promise<string>` (`VirtualModuleSource`); the map type is `VirtualModules`. **Factories are resolved on the host, before the worker spawns** — the node-worker/node-process/bun-process/deno-process runner constructors call `BaseEnvRunner._initWithVirtualData(init)`, which detects function values via `_resolveVirtualData()`, awaits `resolveVirtualModules()`, replaces `data.virtual` with a plain `Record<string, string>`, then runs `init`; a throwing/rejecting factory closes the runner with the error as cause. This is required because functions can't cross the `workerData`/`JSON` boundary and Node's synchronous load hook can't await; the spawn stays synchronous when all sources are already strings. Each worker then `await`s `registerVirtualModules(data.virtual)` **before** importing the entry. On Node.js/Deno this wires `module.registerHooks()` (in-thread, synchronous — the non-deprecated successor to `module.register()`) with hooks from `createVirtualHooks()`; on Bun (which lacks `registerHooks`) it registers each entry via `Bun.plugin()` `build.module()` instead. The entry and its dependencies can then `import` any map key (e.g. `import { x } from "#virtual-import"`). **The entry itself may be virtual**: set `data.entry` to one of the `data.virtual` keys (e.g. `"#entry"`) and its source is served from the map — including when it imports other virtual modules. Since registrations stay active for the thread's lifetime, virtual specifiers (including a virtual entry) also resolve across `reloadModule()` — on the registerHooks backend via a `?__envRunnerReload` query suffix, on Bun via `refreshVirtualModule()` re-registration (Bun matches `build.module` keys verbatim, so a query suffix would not resolve; re-registering busts its module cache). First-step scope: each source resolves to a self-contained ES module string (no transform pipeline, no per-reload mutation of the map; a factory is invoked once on the host, not re-evaluated on reload). **Per-module invalidation:** `invalidateModule(specifier, timeout?)` (on `BaseEnvRunner`, proxied by `RunnerManager`; the `self` runner throws — no virtual-module support) re-runs a factory-valued source on the host and sends `{ event: "invalidate-module", specifier, source? }` over IPC; the worker calls `handleInvalidateModule()` → `invalidateVirtualModule()` and acks with `{ event: "module-invalidated", specifier, error? }`. Invalidation marks the module **and its transitive virtual importers** (`expandVirtualInvalidation()` — without this, a reloaded entry would resolve an intermediate virtual importer to its cached instance, still linked to the old module; disk-file importers follow the ordinary entry-reload semantics and are not tracked). Already-linked importers keep their instances, so callers pair it with `reloadModule()`: the re-imported entry then resolves the invalidated graph to fresh identities (registerHooks backend: per-specifier `?v=<n>` versions appended to the `virtual:` URLs by the resolve hook; Bun backend: source-map update + re-registration of the expanded set). **Through `RunnerManager`/`EnvServer` the pairing is automatic**: `invalidateModule()` marks the manager dirty and the next `fetch()` performs one shared `reloadModule()` before serving (lazy reload — explicit `reloadModule()`/`reload()` also satisfies it). `data.virtual` is typed on `EnvRunnerData`. `registerVirtualModules()` feature-detects `module.registerHooks` via a dynamic import, then `Bun.plugin`, and warns-and-skips when neither exists, so older runtimes (Node < 22.15/23.5, Deno < 2.x) degrade gracefully instead of crashing the worker. (Never detect Bun support via `module.register` — Bun defines it as a silent no-op.) `registerVirtualModules()` resolves to an idempotent **unregister function** that each worker calls in its `shutdown` handler (after `ipc.onClose()`/`server.close()`, before posting `exit`), so a graceful shutdown releases the registration; host-side `close()` terminates the thread/process outright, which drops it implicitly.

**TypeScript and JSON virtual modules** are selected by specifier extension (`virtualModuleFormat()` in `virtual-loader.ts`): `.ts`/`.mts` sources are served as TypeScript (Node native type stripping via the `module-typescript` load format, Bun via the `ts` plugin loader; erasable syntax only on Node), `.json` sources as JSON modules exposing the parsed value as the default export (Node via the `json` load format; Bun via the `object` plugin loader because Bun's runtime `json` loader doesn't parse contents). The `with { type: "json" }` import attribute is **optional on Node/Bun** (custom hooks bypass Node's attribute validation). **Deno caveats** (its `registerHooks` load hooks ignore the returned `format`): `.json` sources are pre-wrapped into `export default JSON.parse(...)` modules by `_transformForDeno()`; `.ts`/`.mts` sources are pre-stripped with `module.stripTypeScriptTypes` (Deno >= 2.8.2) and **throw at registration** on older Deno without it (pass pre-transpiled JS instead); and static imports carrying any import attribute bypass `registerHooks` resolution entirely, so virtual JSON imports on Deno must omit `with { type: "json" }`. (Dead ends, verified: Deno `data:` URLs honor formats but their static imports skip resolve hooks — "not a dependency" — and registering any custom load hook breaks `data:` loading with "Loading unprepared module".)

**Miniflare** takes a different path entirely (no in-worker registration): the `MiniflareEnvRunner` constructor also calls `_initWithVirtualData()`, `#prepareVirtualModules()` pre-strips `.ts`/`.mts` sources on the host with `module.stripTypeScriptTypes` (workerd parses every `esModule` as plain JS; missing stripper → clear `TypeError`), and the `unsafeModuleFallbackService` serves virtual keys **before** any other resolution (so a virtual key overrides a real file and the `transformRequest` pipeline; matched against `rawSpecifier`, `specifier`, and the leading-`/`-stripped specifier, query stripped). `.json` keys are served as workerd-native `json` modules (parsed value = default export); fallback-served modules bypass `modulesRules`, so no extra rules are needed. The reload `?t=<n>` query is kept in the returned module `name` for a fresh workerd identity (verified: workerd passes `#`-prefixed specifiers to the fallback intact, e.g. `specifier=/#entry&rawSpecifier=#entry`). A **virtual entry** skips `resolve()`/`scriptPath` path handling (anchored at cwd for bare-specifier resolution via `entryBase`) and is eval-imported verbatim by the wrapper. **Invalidation on miniflare is host-side only** (no worker round-trip): `invalidateModule()` re-runs a factory source, re-preps it (`#prepareVirtualSource()`, TS strip via the cached `node:module` lookup), and bumps per-specifier versions in `#virtualVersions` for the module **and its transitive virtual importers**; the fallback service rewrites **import specifiers** of invalidated keys in re-served module code (`applyVirtualVersions()`, es-module-lexer — static imports/re-exports and literal dynamic imports including plain template literals; never arbitrary string literals, so code merely mentioning a key as data is untouched; unparsable and CJS-shim responses are served as-is), so after a `reloadModule()` the versioned specifier misses workerd's registry (it caches by name), hits the fallback again, and loads fresh. **`persistent: true` composes with invalidation**: the live `virtual`/`#virtualVersions` maps are owned by the `_miniflareCache` entry — a runner attaching to a cached instance adopts them (so its `invalidateModule()` mutates what the instance's fallback closure actually serves), ref-counting goes through the entry object (`#cacheEntry`, not a key lookup), and invalidating **evicts the entry from the cache** so future runners constructed with the original sources get a fresh instance instead of mutated state. Caveats (verified): workerd rejects **any** import attribute ("Unrecognized import attributes specified") so virtual JSON imports must omit `with { type: "json" }`; miniflare's `ModuleLocator` statically walks the wrapper script, so literal virtual specifiers must never appear in it (`dynamicOnly` mode keeps them out) — consequently named `exports` (DO/WorkerEntrypoint static re-exports) combined with a virtual entry **throw at init**; nothing to unregister (the fallback closure dies with the Miniflare instance); the resolved virtual map is part of the `persistent` cache key.

## Testing

- **`test/virtual.test.ts`** — Tests virtual modules for `NodeWorkerEnvRunner`, `NodeProcessEnvRunner`, `BunProcessEnvRunner` (auto-skipped when `bun` is not installed), `DenoProcessEnvRunner` (auto-skipped when `deno` is not installed), and `MiniflareEnvRunner` via the `data.virtual` map: a virtual import, a virtual entry (`data.entry` = a virtual key), a virtual entry composing another virtual module, TypeScript virtual modules (`.ts` entry + import on Node/Bun/Miniflare/Deno-with-`stripTypeScriptTypes`; fail-fast on older Deno — detected by probing `deno eval` at collection time), JSON virtual modules (attribute-free on all runtimes, `with { type: "json" }` on Node/Bun only — workerd rejects import attributes), factory-valued sources (sync and async), `invalidateModule()` (factory re-run picked up after `reloadModule()`, repeated invalidations, invalidation reaching a module through an **intermediate virtual importer**, rejection for unknown specifiers — all runners incl. miniflare), reload of a virtual entry, graceful worker shutdown with virtual modules registered (skipped on miniflare — no shutdown handshake), miniflare-specific invalidation behavior (string literals merely mentioning an invalidated key are NOT rewritten; invalidation through a runner sharing a `persistent` cached instance), fail-fast for named `exports` with a virtual entry on miniflare, `SelfEnvRunner.invalidateModule()` rejecting with a clear not-supported error, and (via the `virtual-unregister.mjs` subprocess fixture) unregistration on both the registerHooks and Bun.plugin backends. **Note:** runner tests spawn workers from `dist/` (runners resolve their co-located worker via the self-linked `env-runner` package), so worker-side changes need `pnpm build` before `vitest run`
- Test fixture in `test/fixtures/app-virtual.mjs` — Entry that imports `#virtual-message` and returns its `message` export as the response body
- Test fixture in `test/fixtures/virtual-unregister.mjs` — Subprocess script (run with node/bun) asserting `registerVirtualModules()`'s unregister function releases the registration (vitest's module runner intercepts in-process dynamic imports, so this can't run in-process)
