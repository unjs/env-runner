# Plugins (`plugins` runner option)

Host-side `resolveId`/`load`/`transform` plugins for the entry, its imports, disk modules and virtual modules. User docs: README "Plugins (`plugins`)". A top-level runner option (also on `LoadRunnerOptions` and `EnvServerOptions`), never part of `data`, since plugins are host objects.

- **`src/plugin/pipeline.ts`** (host) — public types (`EnvRunnerPlugin`, `PluginHook`, `PluginTransformFilter`, `PluginHookFilter`, `PluginTopLevelFilterExpression`, ...), `createPluginPipeline()` (flattens `plugins`, validation, per-hook `pre`/normal/`post` ordering, filters compiled to their serialized form, async handlers wrapped as `[env-runner] plugin "<name>" failed on "<id>"` / `failed to resolve` / `failed to load`, `this.warn`/`info`/`debug`/`error` with positions, source maps, output `moduleType` `js`/`ts`/`json`, error for leftover JSX) and `transformVirtualModules()`. Hooks: `resolveId` (first result wins; `false`/`external` → runtime), `load` (first code wins, then `transform`; no code → `read()` the file, or throw for non-file ids; non-file ids reach every matching `load` hook whatever their type), `transform`. Plugins are sorted by `enforce` (stable) before hooks are grouped by `order`. `resolveId` hooks with `fallback: true` form a second phase (`resolveId(source, importer, { fallback: true })`, `resolveFilter(source, true)`, `fallback: true` on their serialized prefilter), asked only after the runtime failed. The context also has `resolve()` (normal hooks → `_resolveLikeRuntime()`: exsolve, strict like Node ESM, `cache: false`, the runner's `_resolveConditions()` (Bun/Deno/miniflare override it), builtins external → `fallback` hooks; `skipSelf` (default) skips the calling `resolveId` hook for its call and for nested calls with the same source and importer, as `ResolveSkip` entries), no-op `addWatchFile`/`getWatchFiles` and `meta: { watchMode: false }`. Handler errors (`_callHook()`) and log objects keep a `loc`/`pos` (as `id:line:column` in the code the hook got) and a `frame` (below the message); only the message string crosses the channel. `PluginResolvedId` is a type alias, so `resolveId` handlers can return `this.resolve()`'s result. Plugins without supported hooks are accepted (other hooks ignored; with no supported hook at all, `createPluginPipeline()` returns `undefined`, as without `plugins`); `resolveId`/`load` filters take `id` only, and `resolveId` globs aren't resolved from cwd (they match specifiers)
- **`src/plugin/glob.ts`** (host) — `resolveGlob()` (from cwd unless `**`-prefixed or absolute, once, when the pipeline is created; cwd is glob-escaped; on Windows an absolute glob with only `\` separators has them converted, one using `/` keeps `\` escapes) and `globToRegExp()`: anchored, `*`/`**` match dot files, `\` escapes, `[!..]`, nested/single `{..}`, no extglobs, case-sensitive; `/` compiles to `[\\/]` (and `*` to `[^\\/]*`) so the RegExp also matches Windows paths on Bun
- **`src/plugin/filter.ts`** (shared) — `node_modules` (`isNodeModulesId()`: only for filters whose `id` includes name `node_modules` (`nodeModulesIncludes()`) and one of those matches, or `resolved` paths a `resolveId` returned; not for `resolveId` filters or virtual modules), `moduleTypeOf()` (`js`/`ts`/`jsx`/`tsx`/`json`, else the extension, `js` without one), match levels (`compilePrefilter()` → `false`/`true`/`"named"` (an `id` include matches; in expressions, the matching include's `id` or present `query` param)/`"typed"` (the `moduleType` filter lists it, or the matching include's `moduleType`; a `load` filter's `id` include counts as typed; expressions without code take the highest level a possible outcome has, exact on the host with the code); `requiredMatch()`: scripts need any match, `json`/`node`/`wasm` `"typed"`, other types `"named"`), serialized filters (`SerializedPrefilter`: `id` patterns as RegExp `{ source, flags, glob? }`, `g`/`y` dropped; `moduleTypes`; or `expr`, the filter expressions), `compileFilterExpressions()` (three-valued: a `code` leaf without code is unknown; the first include/exclude that matches decides, an unknown before it makes the result unknown) and `createPrefilter()` (sends unless the result is `false`)
- **`src/plugin/channel.ts`** — the sync request channel (host `openTransformPort()`/`openTransformSocket()`, worker `createTransformClient()` → `{ resolve, load }`)
- **`src/plugin/hooks.ts`** (worker) — `registerPluginHooks()`, `transformedFormat()`, `createBunFilter()`, `createBunResolveFilter()`, `resolveSchemes()`, `servedByPluginHooks()` (Bun reloads)

## Flow

1. `BaseEnvRunner` constructor: `createPluginPipeline(opts.plugins)` (throws `TypeError` for invalid plugins; `undefined` without any supported hook, e.g. `plugins: []`) into `_plugins`. Every runner forwards its `plugins` option to `super()`; `EnvServer` passes its own to each runner it creates.
2. Virtual modules: `_resolveVirtualData()` takes the async path when there are plugins (resolve factories → `transformVirtualModules()`), and `_enqueueVirtualUpdate()` transforms the resolved changes before storing and sending them. `_virtualSources` keeps the originals, so `invalidateModule()` re-transforms. Output format: `commonjs` for CommonJS formats, else `module` (`*-typescript` when the output is still `ts`).
3. `_pluginWorkerData(kind)` adds `data.__envRunnerPlugins = { prefilters, resolvePrefilters, ...channel }` (`prefilters`: `load` + `transform` filters) (`PLUGINS_DATA_KEY`) and opens the channel once (`_transformChannel`, closed in `close()`): `"port"` from `NodeWorkerEnvRunner.#initWorker()` (the port goes in `transferList`), `"socket"` from `_processEnv()` (so every process runner gets it through the init-data JSON).
4. Workers call `registerWorkerHooks(data)` (`worker-utils.ts`) so virtual keys win over the plugin hook (their sources are already transformed): `registerPluginHooks()` then `registerVirtualModules()` under `registerHooks` (the latest registration runs first), the reverse on Bun (the earliest `onLoad` whose filter matches wins). Bun's dynamic virtual keys are served with a marker query, which the plugin filter excludes.
5. An import the `resolveId` prefilter matches sends `{ type: "resolve", source, importer, isEntry, attributes }` and blocks for `{ id, resolved? }`: an absolute path is served as its `file:` URL, another id as `env-runner-plugin:<encoded id>` (Bun: that namespace), `external` goes to `nextResolve()` (with the returned id). Imports from plugin ids resolve from cwd. `isEntry` compares the specifier with `data.entry`.
6. A load of a candidate the prefilter matches sends `{ type: "load", path }` (the path with the import's query; plugin ids: `virtual: true`), and blocks for `{ id, code?, moduleType? }` (no `code`: unchanged, fall through to `nextLoad()` / Bun's native loader) or `{ id, error }` (thrown from the load). The runner reads the file without the query (`pipeline.load(path, read)`). `json` output is served as format `json` when the import has `type: "json"` attributes or is a `require()`, else as `jsonModuleCode()` (default export plus top-level keys as string-named exports; Bun: an `object` module with the keys; miniflare: the same ES module). Node/Deno remember paths `resolveId` returned (`pluginResolved`) and send them as `resolved` (node_modules opt-in); Bun loads resolved node_modules and other-type paths in `onResolve`.

## Queries

Ids keep the import's query everywhere plugins see them (`resolveId` source and importer, `load`, `transform`, filters), and the query stays part of the module's identity. Filters: `id` globs and RegExps both match the full id, query included (only the path part is `/`-normalized); `query(key, pattern)` parses `URLSearchParams` from the query without its fragment (`true`/`false`: `has(key)`, string: `get(key) === pattern`, RegExp: `test(get(key) ?? "")`). `moduleTypeOf()` and the `node_modules` check (`isNodeModulesId()`) look at the path. Source map `sources` use the id without its query.

env-runner's own params are removed before an id reaches a plugin (`stripInternalQuery()`), keeping the rest of the query as written:

- by name: `__envRunnerReload` (`_importFresh()` and the miniflare wrapper's reload), the Bun markers `__env_runner_virtual`/`__env_runner_disk`/`__env_runner_plugin` and miniflare's `__cjs` shim request;
- virtual module versions only when the module is versioned (`v=<n>` is also a plausible user param): the trailing `v=<n>` whose `n` is the current version, from `virtualFileVersion()` (`registerHooks`: disk files by bare `file:` URL; Bun: path keys and removed ones by path) or, on miniflare, `_virtual.versions` for the (removed) key the specifier refers to.

A `resolveId` result gets the source's internal params back (`restoreInternalQuery()`), so a reload through a resolving plugin still busts the cache.

Per runtime (verified on Node 24, Deno 2.9.6, Bun 1.4.2 and miniflare v5):

- **Node/Deno**: the load hook gets the `file:` URL with its query; `_fileId()` turns it into the id. `./a.ts` and `./a.ts?raw` are separate modules (the registry is keyed by URL).
- **Bun**: keeps a path's query in `onLoad`'s `path` and in the module's identity (a `file:` URL's query is dropped: reloads import paths), and resolves a static import twice before loading it (so `loadOther()` reuses a pending result). The `onLoad` filter allows a query after the extension (`[^?]*` before it, so `a.txt?x.ts` isn't a script) unless a Bun marker leads it; other file types keep their query behind the `__env_runner_plugin` marker (`<path>?__env_runner_plugin&raw`).
- **Miniflare**: the module name keeps the query (so `dep.ts?raw` is its own module); the plugin id is the resolved path plus the import's query (or the id a `resolveId` hook returned), which also keys `_cjsOutput` and `_pluginModuleIds` (importer ids). The CommonJS shim imports `./<file>?<query>&__cjs`.

## Transport

Loader hooks are synchronous (`registerHooks`, and Bun's `onLoad` under `require`), so the worker blocks with `Atomics.wait` on a shared `Int32Array` counter and reads the reply with `receiveMessageOnPort()`. The runner IPC channel can't carry the reply: its listener runs on the blocked thread. Async hooks aren't an option either: Deno and Bun have no `module.register()`, and Node's off-thread hooks deadlock on `require`.

- **node-worker** (and vercel/netlify): a `MessageChannel` + `SharedArrayBuffer` created by the runner. The runner's port answers directly (`port1.unref()`, closed with the runner), then bumps and notifies the counter.
- **Process workers**: the runner listens on a fresh local socket, `transform.sock` in a `mkdtemp` directory (0700, so other users can't connect; `/tmp` when `$TMPDIR` makes the path too long for a unix socket; a `\\.\pipe\env-runner-<pid>-<uuid>` named pipe on Windows). It accepts only the first connection (the worker's), then closes the listener and removes the directory at once, so a signal can't leak it and no other client can connect; before that, `close()` and process exit remove it. A malformed line destroys the connection. The worker connects after the init-data handshake, by which time the socket is bound. The worker starts an eval helper `Worker` (CommonJS source string, no extra dist file; eval workers work on Node, Deno and Bun) that connects and relays newline-delimited JSON between the socket and a `MessagePort`, notifying the counter per reply. The helper is `unref()`d. When the socket closes, or the helper throws (`uncaughtException`), it answers every request with `{ closed: true, error }`, so a blocked load throws instead of hanging.
- Requests are sequential (one blocked thread), so a reply with a different `id` is stale and skipped. The client reads the counter before each `receiveMessageOnPort()` (a reply posted in between makes the wait return at once) and waits in 10 s slices, warning once per slow module. A handler awaiting its own runner (`fetch()`, `rpc()`) blocks it indefinitely.
- Verified on Node 24, Deno 2.9.6 and Bun 1.4.2 (`Atomics.wait` on the main thread, `SharedArrayBuffer` in `workerData`, eval workers, `node:net` unix sockets from a worker thread).

## Per runtime

- **Node/Deno** (`registerHooks`): a resolve hook only with `resolveId` hooks (sees every specifier; verified on Node 24 and Deno 2.9.6, including custom-scheme URLs and their relative imports rebased to cwd). Load: `file:` URLs (id: path + the import's query) and `env-runner-plugin:` URLs. Output format via `transformedFormat()`: the resolution hint when definite (`module*`/`commonjs*`), then `.m*`/`.c*` extensions, then CommonJS markers + no ESM syntax (es-module-lexer). `ts` output is served as `module-typescript`/`commonjs-typescript` on Node. Deno parses hook output as plain JS, so `ts` output is stripped (`module.stripTypeScriptTypes`, Deno >= 2.8.2) and CommonJS wrapped with `commonJSToESM()` (the virtual modules' wrapper, `virtual-modules.ts`). Untouched CommonJS goes to Deno's native loader (`--unstable-detect-cjs`), and `require()` reads files from disk.
- **Bun** (`Bun.plugin` `onLoad`, can't be removed): one filter RegExp from `createBunFilter(prefilters)`: one alternative per plugin with the extensions its `moduleType` implies (all non-CommonJS ones for filter expressions; never `.cjs`/`.cts`), `id` excludes as negative lookaheads and includes as lookaheads (compiled globs everywhere, user RegExps only off Windows, where they'd see `\`; not folded when flags differ or a source has backreferences/named groups), `/node_modules/` (in the path) and Bun marker queries excluded, an optional query after the extension. Paths the RegExp passes but the prefilter doesn't are served with the loader Bun would use. Bun evaluates `onLoad` contents as ESM, so CommonJS (by `transformedFormat()`, transformed or not) is wrapped with `commonJSToESM()`; `ts` output uses the `ts` loader. `_importFresh()` evicts `require.cache` for plugin-served entries. Other file types never reach that `onLoad` (it can't decline, and runtime `onLoad` can't reproduce Bun's native loaders: `text`/`css`/`file` are rejected, `toml`/`yaml` give no default export, verified on Bun 1.4.2). They are loaded in an `onResolve` for specifiers with a non-script extension (`BUN_OTHER_FILE`; relative/absolute only, resolved against the importer): when the prefilter matches and the runner returns code, the file is served as `<path>?__env_runner_plugin[&query]` from a marker `onLoad`, else the callback declines and Bun loads it natively. A `resolveId` returning a non-script path does the same. Plugin JSON on Bun is an `object` module with top-level keys as named exports. Imports: `onResolve` with `createBunResolveFilter()` (the `id` includes, else `/.*/`), skipping Bun's re-resolution of returned paths (empty importer), plus one `{ namespace: scheme }` callback per `resolveSchemes()` entry, since Bun routes `scheme:rest` specifiers only there (verified on Bun 1.4.2). Bun never calls `onResolve` for bare specifiers whose last `.` isn't followed by a letter (`~icons/home`). Plugin ids are served in the `env-runner-plugin` namespace.
- **Miniflare**: no channel. The module fallback service runs the plugins of the live runner (`ipc.runner._plugins`, swapped when a persistent instance is adopted): `resolveId` after virtual modules (importer: the referrer's path, or its plugin id from `_pluginModuleIds`; plugin ids are served under the specifier's name, ESM or `commonJsModule`), then `load`/`transform` on disk modules `transformRequest` returned no code for (id: the path + the import's query) (a missing file a plugin loads is not a 404; `json` output is a `json` module; workerd rejects import attributes); `ts` output is stripped on the host, and CommonJS output (`transformedFormat()`) goes behind the ESM shim (its output is kept for the shim's `?__cjs` request, so it is transformed once). Errors are logged on the host and served as a module that throws (a named import fails at link time first, hiding the message from workerd). v4 adds `.cts` to the `modulesRules` it adds for `.ts`/`.tsx`/`.jsx`/`.mts`. The persistent-instance cache key includes whether there are plugins (they change the v4 module rules).
- **Self**: closes with `Cannot use plugins` (a worker must block while the host runs the plugins).

`fallback` resolveId hooks per runtime: Node/Deno call `nextResolve()` first and ask the runner when it throws or (Deno, which resolves missing files and fails at load) returns a `file:` URL without a file; Bun's `onResolve` runs before Bun resolves, so it asks `Bun.resolveSync()` first, with `_bunResolving` set because `resolveSync()` re-enters the plugins' `onResolve` (infinite recursion otherwise; Bun resolves extensionless relative imports itself); miniflare asks where its host resolution fails (bare: before the empty stub; `_require.resolve()`: before the 404; a relative/absolute/`file:` path without a file). On miniflare, a `resolveId` result that is a virtual path key is redirected (301) to the key's path, like `file:` imports of it, and a disk `.wasm` no plugin loaded is served as a `wasm` module (workerd can't compile bytes).

Measured cost (N=400 small modules, i7-10700K, Node 24.21, Bun 1.4.2, Deno 2.9.6; startup median of 6): a matching `transform` about 50 µs per module on node-worker, 200 µs on node-process/Bun, 280 µs on Deno (process runners also pay ~10–30 ms once at startup); returning nothing costs slightly more than returning code on Node (the worker then reads the file itself); a `resolveId` returning `null` about the same per import; no matching filter ~20 µs/module (node-worker), ~50 µs (Bun), ~115 µs (Deno: a JS load hook on every module). `reloadModule()` sends only the entry (dependencies stay cached in the runtime); nothing is cached on the host. Miniflare's numbers are dominated by its fallback service (every module goes through it anyway).
